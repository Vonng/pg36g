# 第一轮：Opus 5 全面反方审查

## 一、评审者总体判断

评审者认为，v2 的教学骨架明显优于多数同类中文数据库书，尤其肯定：

- ch31 作为统一事故入口、ch32-ch35 作为并列分支；
- 每章明确边界和“不讲什么”；
- ch17 先证明单机已经到边界；
- “成本不是时间”“顺序扫描不自动等于坏计划”“HA 不能替代备份”等反直觉判断；
- 取消每章强制生成 YAML 交接包；
- 恢复必须在隔离环境执行；
- 明讲 PostgreSQL 不应该替代什么；
- 选择电商与支付作为主案例；
- 为动作定义观察、可逆变更、破坏性演练三级风险。

但它认为当前目录还不是一个成立的出版工程，主要风险是：

1. Pigsty 的知识对象与参考实现身份没有讲清；
2. v2 编号与现有站点、页面和提示词冲突；
3. 实验规格、成本、版本、数据与随机种子没有形成契约；
4. 650 余个主题和 185 套实验产物带来写不完的风险；
5. 扩展篇与性能实验的承诺超过当前环境可复现能力；
6. 统一六节三点的网格已经开始反向塑造内容。

## 二、BLOCKER 摘要

### B1 Pigsty 依赖契约不清

评审者主张：卷首称 Pigsty 为实验环境，但 ch19-ch36 中 Pigsty 已经成为知识对象。若不声明，会让读者误以为这是一本伪装成 PostgreSQL 书的 Pigsty 手册。

建议：

- 每章标注“纯 PostgreSQL / 任意平台 / Pigsty 特有实现”；
- Pigsty 小节统一写成“平台应提供什么 → Pigsty 如何实现 → 其他平台的等价能力”；
- 每个面板结论给出 PostgreSQL 原生 SQL；
- 序言披露作者与 Pigsty 的关系。

### B2 新编号与现有资产冲突

评审者指出：v2 将现有 ch01 降为 ch0，并调整 ch01-ch18 多个编号；现有 `/chNN` URL、ch02 已写页面和 36 份提示词都采用旧编号。

它的理想建议是：

- 放弃重排；
- 保留“扬帆起航”为 ch01；
- 合并 v2 的 ch03/ch04；
- 保持既有 36 个编号不动。

若坚持重排，至少要：

- 建立旧版与新版映射；
- 将旧版归档到版本化路径；
- 更新站点、提示词、交叉引用和已写页面。

### B3 实验环境撑不起性能结论

评审者指出：

- L1/L2/L3 没有 CPU、内存、存储、网络和成本契约；
- 小规格虚拟机上的分布式、容量、`work_mem` 和 P99 结论容易被虚拟化噪声主导；
- 向量、时空、备份、WAL 和多个索引可能超过小盘容量；
- 三节点加克隆环境的成本没有披露。

建议：

- 为 L1/L2/L3 建立经过实测的资源档位；
- 性能章节只承诺方法和相对变化；
- 作者提供一组真实规格参考数据；
- 增加“如何判断测到的是 PostgreSQL 还是虚拟机”。

### B4 向量检索实验缺少可复现的向量来源

评审者指出：在线 embedding API 会引入费用、密钥与版本漂移；本地模型超出小环境能力；随机向量又无法评估召回质量。

建议：

- 随书冻结商品文本、预计算向量、模型元数据、校验和与小型标注评测集；
- 将“如何生成 embedding”降为附录或外部任务；
- 正文只讲 PostgreSQL 检索建模、索引、质量和性能验证。

### B5 缺少版本契约

评审者指出：Pigsty 面板、Playbook、扩展、PgBouncer 语义等都比 PostgreSQL 原理更快腐烂。

建议：

- 冻结 PostgreSQL / Pigsty / OS / 扩展版本四元组；
- 建立在线勘误和兼容矩阵；
- 面板讲指标语义，不依赖点击路径；
- 每个 Pigsty 观察结论都配原生 SQL。

### B6 篇幅和产能超载

评审者估算：667 个三级主题可能形成 40-53 万字、1000 页以上的双卷书；每章五类实验文件意味着约 185 套脚手架，而当前尚未创建 `labs/`。

建议：

- 先完整写 ch08、ch20、ch32 三种章型，获得真实字数与工时；
- 完整脚本放伴随仓库，书中只保留入口、关键片段和验收；
- 区分机器断言与人工证据审查；
- 它倾向将扩展篇六章压成四章，并将正文压到 30 万字以内。

## 三、MAJOR 摘要

分区同时影响建模、主键、执行计划、在线改造、Vacuum 和生命周期。建议在 ch04、ch07、ch11、ch28 形成贯穿线，或独立成章。

正文实际需要 CTE、LATERAL、窗口函数、FILTER、物化视图和复杂系统视图查询。建议将假设改为“熟练 SQL”，并提供不讲授但会使用的 SQL 特性索引。

### M6 事故分支缺少若干真实故障

评审者点名：

- XID 回卷紧急态；
- 磁盘或 WAL 打满；
- 复制槽不消费；
- collation 版本变化；
- DCS/etcd 故障；
- OOM Killer。

建议在分诊图与书末故障速查表中明确路由。

### M7 RLS 与连接池被割裂

PgBouncer transaction 模式下使用不当的会话级 `SET` 可能泄漏租户上下文。建议 ch12 讲连接池语义，ch22 讲接入架构，ch23 明讲 `SET LOCAL`、事务边界与 RLS。

### M8 扩展篇主题密度过高

ch15 同时承担全文、向量、ANN 与混合检索；ch16 同时承担分区、时序扩展、PostGIS 与时空优化；ch17 同时承担并行、只读、列存、CDC 与分布式。

建议至少将目标从“掌握”降为“能判断、能做最小 PoC、知道生产代价”。评审者更偏好将六章压成四章。

### M9 ch14 的 ADR 框架没有在后续复用

建议 ch15-ch17 每章都加入扩展 ADR 摘要，覆盖许可、生命周期、备份、升级、退出成本，并在书末汇总。

### M10 Go 服务被迫跨越过多章节

建议 Go 服务只用于 ch12 展示数据库契约如何落地，不承担 ch15-ch34 的长期运行；后续性能和事故注入使用版本化 SQL 工作负载与 pgbench。

### M11 数据集生成器无人负责

建议在早期引入固定随机种子、规模因子和可控均匀/倾斜分布，并让所有性能章节复用同一个生成器。

升级、PITR、集群重建和坏页抢救必须销毁重建或回滚主机快照。建议分为：

### M13 阅读路线未校验前置依赖

ch03 产出逻辑模型 v0 与金额、时间、状态、标识四项未决清单；ch04 逐项闭合为可靠物理模式。两章都在真实数据库中运行，网站版 ch03 标出过渡性质。

### 6. ch06 规约是活文档

ch06 教读者如何依据证据形成规约，产出 baseline v0.1；ch07–ch11 逐章追加有证据的规则；ch12 汇总为 v1.0。

### 7. 分区采用五触点螺旋

ch04 决策门 → ch07 裁剪与统计 → ch11 在线分区化 → ch16 时序应用 → ch28 生命周期维护，并提供分区能力索引。

### 8. 扩展章降承诺并去重

ch15–ch17 以 ADR、最小 PoC 与生产代价为验收，不设脱离场景的性能达标线。ch17 只保留“证明单机边界 → 单机分析加速 → 分布式选型 PoC”，把复制、路由、多集群内容归还下卷。

### 9. ch34 先判流量型或保留型

流量型才进入限流、取消、摘流、降级；保留型只做安全保护并路由 ch21/ch28/ch35。速查表单列 XID 回卷、WAL 撑盘与“绝不手工删除 `pg_wal`”。

### 10. `amcheck` 跨章落位

ch28 用于日常维护检查，ch30 用于升级前验证，ch35 用于索引、坏页和排序规则异常分类，并与 checksum 的职责边界分开。

### 11. 重排与站点迁移解耦

接受为认知顺序重排。语义 slug、`/chNN` alias、giscus 讨论迁移、章节元数据单一事实源和编辑链接修复进入实施清单；目录确认前不直接改站点。正文交叉引用不得只写裸章号，必须同时带功能标题。

### 12. 容量与版本共同校准

ch08、ch20、ch32 三种样章校准字数、实验工时、版本迁移工时和维护成本；定稿前执行“版本增量通过”。若预计工期超过 18 个月，依次削减在线延伸、ch15–ch17 专项深度，最后才调整章数。

## 讨论结论

三轮对抗评审已全部收敛，没有需要用户拍板的目录分歧。最终目录应以这十二条为硬约束。

## 脚手架实施勘误

在 2026-07-29 的 Hugo/Hextra 实际渲染中确认：Hextra 会把内容文件路径 `docs/...` 自动追加到 `params.editURL.base`。因此基地址若写成 `.../edit/main/docs`，最终会错误生成 `.../edit/main/docs/docs/...`。实际正确配置是仓库根编辑入口 `https://github.com/Vonng/pg36g/edit/main`。这一结果以浏览器渲染证据为准，修正第二轮关于 `editURL.base` 应直接指向 `docs/` 的推断。
