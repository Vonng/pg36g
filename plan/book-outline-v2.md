# 《PostgreSQL 36 计》全书架构与目录草案 v2

> 定位：以 PostgreSQL 为知识主体，以 Pigsty 为可重复实验环境、可观测窗口与生产参考实现，完成从应用开发到生产运维、再到故障恢复的全链路实践。

## 一、读者假设

正文默认读者已经具备：

- Linux、Shell、SSH 的基本使用能力；
- 基础 SQL 能力，包括常见 DDL、CRUD、连接、聚合与子查询；
- 至少一种后端编程语言的使用经验；
- 对数据库有使用经验，但不要求系统掌握 PostgreSQL。

不满足上述条件的读者，可以先阅读“第 0 章：扬帆起航”。第 0 章属于可跳过的预备章，不计入正式的 36 章。

## 二、贯穿全书的教学模型

每章都遵循同一条认知路径，但不强制使用完全相同的小节数量：

1. 从一个真实问题或失败现象出发；
2. 先跑通最小可用闭环；
3. 用 PostgreSQL 原生接口观察事实；
4. 解释背后的 PostgreSQL 原理；
5. 映射到 Pigsty 的配置、服务与可观测界面；
6. 注入一个可控故障或反例；
7. 验证结果并恢复实验基线；
8. 说明生产环境中的风险边界。

## 三、贯穿全书的案例与实验环境

### 主线案例：`pg36_shop`

一套逐章演进的电商与支付系统：

- 筑基篇：用户、商品、订单、订单项、支付的基础模型；
- 应用篇：订单查询、库存扣减、支付幂等、模式演进与后端服务；
- 扩展篇：商品搜索、向量推荐、时空配送、实时风控与分析计算；
- 规划篇：将应用部署为生产级 PostgreSQL 服务；
- 维护篇：观测、压测、调优、清理、迁移与升级；
- 出山篇：误更新、主库故障、连接风暴、数据损坏与事故复盘。

### 三层实验拓扑

- `L1`：单节点 Pigsty 开发沙箱，用于 ch01-ch18；
- `L2`：三节点、可销毁的 Pigsty 生产仿真环境，用于 ch19-ch30；
- `L3`：由快照克隆的故障演练环境，用于 ch31-ch35。

每章实验目录统一提供：

- `setup`：建立确定的实验起点；
- `exercise`：实验主体；
- `verify`：机器可验证的验收；
- `reset`：恢复到下一次可重跑状态；
- `expected`：关键输出样例。

## 四、推荐阅读路线

- 开发者主线：第 0 章（可选）→ ch01-ch18；
- DBA 主线：第 0 章（可选）→ ch01、ch02、ch05-ch10 → ch19-ch36；
- 架构师主线：ch01、ch06、ch12、ch14、ch17-ch24、ch36；
- 完整路线：按 ch01-ch36 顺序阅读。

# 五、成书时的统一章型

每章首页固定包含以下信息，但这些内容不一定全部进入纸质目录：

- 本章解决的问题；
- 读完后能完成的可验证任务；
- 必备前置章节和可选前置章节；
- 实验拓扑、预计耗时与风险等级；
- 本章 PostgreSQL 原理范围；
- 本章 Pigsty 映射范围；
- 明确不讲什么；
- `setup / exercise / verify / reset` 入口。

每章正文建议控制为：

- 5-7 个核心二级小节；
- 每个二级小节 2-4 个三级主题；
- 1 个贯穿主实验，最多 1 个反例或故障支线；
- 1 份章节产出，不再强制向下一章生成 YAML 交接包；
- 只有每篇末章生成一次阶段性基线或交付物。

# 六、范围控制与职责边界

- ch02 只教可复现日常工具链，不覆盖生产监控、连接路由或迁移平台；
- ch05 只建立查询、事务与锁的心智模型，计划细节在 ch07，并发异常在 ch10；
- ch07 解决“给定 SQL 如何读计划”，ch08 解决“系统变慢时如何找主因”；
- ch09 负责索引设计和效果验证，ch11 负责在线发布，ch28 负责维护与膨胀；
- ch12 使用一个 Go 参考服务，但数据库原则保持语言无关；
- ch13 先讲 PostgreSQL 原生可编程能力，ch14 再进入扩展生态；
- ch20 负责高可用，ch21 负责备份，明确 HA 不是备份；
- ch25 负责可观测和诊断，ch31 负责告警后的事件响应；
- ch31 是统一事故入口，ch32-ch35 是并列故障分支；
- ch36 统一收束所有事故分支，并将改进固化回 Pigsty 平台。

# 七、建议的内容生产顺序

1. 先完成第 0 章、ch01、ch02，冻结实验环境与写作口径；
