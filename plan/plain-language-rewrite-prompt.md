### 3. 每一处文字只用这一个判据

> **删掉它，读者会做错什么？读者会漏掉什么重要信息？**

答不上来，就删掉；有信息但难懂，就重写；删后暴露知识缺口，就核实后补上。

回答必须具体，例如“会把事务回滚误当成撤销外部付款”“会把连接池地址误认成后端实例”“会在恢复前覆盖唯一副本”“会缺少解释查询等待的关键原因”。“不够严谨”“不够完整”“怕被误解”不构成保留理由。

这条判据同样适用于标题、首段、结尾、表格列、图注、警告框、脚本说明和章级学习目标。不能只在正文散文里找词。

文字长短由问题决定。不规定删减百分比、每页字数、段落数量或否定词配额。解释充分的长段可以保留；一整节都没有内容时可以重写。不要为了缩短把句子删成电报体，也不要虚构经历、脏话、俏皮话或作者观点来制造“人味”。

### 4. 重点清理什么

**无意义的否定和对照。** 重点检查“不是……而是……”“并不意味着”“不能据此”“不应该理解为”“不要把……当成……”“真正的……”。如果被否定的东西与本页问题无关，直接删掉，正面说清规则。对真实、容易发生的技术混淆，保留区分及后果，优先写清适用条件。不要把所有“不”字机械清零。

**免责声明和训导。** 删除“应当树立意识”“成熟工程师应该”“不能只会敲命令”等评价读者的句子。删除没有具体作用的“仅供参考、请自行判断、不能直接外推、以实际为准”。实际的破坏范围、版本条件、权限要求、停止条件和恢复步骤放在相应操作附近，简洁写清。

**稻草人和虚假争论。** 不要先发明一种蠢做法再纠正它。例如讲案例递进，直接说前一章的数据和配置怎样供后一章使用；无需反驳“玩具应用能覆盖一切”。

**抽象黑话和中英混写。** 把“形成闭环”“交付契约”“治理能力”“证据驱动”“权限边界”等空泛表述落实到对象、动作和结果。实际协议名、API、参数、字段、文件名保持准确；普通叙述中的 `owner`、`authority`、`gate`、`contract` 等按语境说成负责人、操作权限、检查条件或具体约定。重要术语首次出现给中文解释和必要英文原词，后文统一称呼。

**模板和重复。** 删除无新增信息的本节小结、学习收获、下一节预告、三项排比、重复警告和跨平台旁白。目录与章首页只做必要导航和定位。不要要求每节都出现“目标—前置—边界—反例—证据—验收—总结”七件套。

**绕过答案的开头。** 页面需要摘要时，description 用一两句说明实质内容；首段直接回答该页问题或指出具体症状与处理入口。不要把 description 原样复制到首段，也不要在正文重复页面一级标题。概念页可以从现象解释起，不要求每段第一句都写成结论口号。

**空泛保留词。** “通常、可能、一般、往往、视情况而定”确有条件时，说明是什么条件；只是在回避判断时，查清楚再写。真实不确定性应保留，不能把概率或条件说成确定事实。

### 5. 把教程从实验报告中整理出来

逐章区分三个东西：通用机制、读者可复现的实验、作者某次运行的记录。

- 正文讲清机制、步骤、结果判读与重要限制。
- 实验正文保留必要的环境、权限、命令、关键输出、失败分支和复位方法。步骤能在页面内读明白，完整长脚本通过链接取得。
- 某次测试的审批状态、负责人、证据清单、完整输出和例外编号，放在对应实验记录中；正文仅引用影响结论的部分。移动文字时同步修好链接，保留原记录和来源信息。
- `pending`、`approved`、`passed` 等只有在确实是脚本输入或输出时，才需要原样展示并解释。编辑工作流状态不得成为读者学习数据库的前置手续。

可以删除重复的“没有证明什么”，但要把测量范围留在数字旁边。例如一次健康计划切换的采样写入间隙，要交代测量方法和未覆盖的故障检测阶段，不能把它改称生产 RTO。没有可靠记录支持的数值，先核实或撤下相关断言。

必要的限制可以出现在多个独立入口：如果读者只读当前操作页就可能误用危险命令，应在本页保留最短、具体的条件。不要为了去重把关键限制藏到远处导读。

1. **完整阅读。** 读正文、表格、图注、代码解释及必要的上下文，写明本页解决的问题。关键词搜索只用于定位，不能代替通读。
2. **删改和补写。** 逐段过删除判据。完成后作者自读，检查推理连续、示例可用、限定准确。自读是作者工作，不算独立审阅。
3. **独立技术审。** 另一位审阅者检查完整新稿与差异，回到原始来源核对改动影响的事实、限定、命令和输出。没有新增事实的纯措辞修改重点查语义漂移，不强制重跑全部实验。
4. **独立语言与静态审。** 第三位审阅者通读新稿，按两问标出需返修之处，检查结构、术语、链接、图表和读者能否完成该页任务，由作者返修后复核。与作者和技术审阅者分开；审阅者若直接重写，改写部分交给未参与写作的人终审。只看作者总结或改词数量不算审过。
5. **主控接收。** 对照实际差异和审阅结果安装到共享稿，记录验收版本。返修涉及事实时补技术复核；不能拿返修前的通过记录覆盖新稿。

若暂时没有独立审阅者，保留“待独立审阅”，继续其他已授权的工作，不自称三审完成。不要为每句话建立单独审批表，也不要机械照搬其他书的 frontmatter 字段。

现有 `book_status: reviewed` 只是旧稿状态。实质重写后使用本书自定义字段 `book_status: draft` 标识待审，验收后再提升为 `reviewed`。它与控制 Hugo 发布的 `draft: true` 是两个字段，后者保持既有发布设置；细分审阅进度记在台账中。

### 10. 批次顺序

先用四类页面建立尺度：一篇入门概念、一篇查询诊断、一篇运维原理、一篇恢复实验。对每篇给出少量有代表性的前后对照，通过独立审阅后继续推进，不把样章当作全书交付。

随后按以下顺序处理：

1. 序言、全书导读、首页、上下卷导读，删掉全书层面的重复训导。
2. 第 0 章和 ch01–ch18，连同对应实验说明，重点补清概念、SQL 与输出之间的关系。
3. ch19–ch30，重点拆开通用机制、Pigsty 实现、某次实验记录与审批话术。
4. ch31–ch36，重点写清症状、判断、动作、停止条件和恢复结果，去掉重复的“未证明”清单。
5. 附录、目录、索引、README、首页与导航文案，核对正文修改后的称呼和链接。
6. 逐篇比对历史稿、同步现行生成规则、检查所有实际存在的阅读版本。

每批完成就更新同一台账。会话中断后从未验收文件接续，不重开一轮统计、不抹掉未解决问题。

### 11. 工程验收

构建基线保持 Hugo Extended 0.168.0、OINK v1.3.2。不要套用美国生活书的版本或政策复核日期。`make dev` 使用本地主题，不代表发布锁定版本已经通过。

主控在相关批次接收后运行 `make check-book`；完成结构或共享元数据修改，以及全书收尾时运行 `make check`。查看警告，修复新增的路径和渲染问题；不启用 `--panicOnWarning` 或 `HUGO_PANICONWARNING`，已接受的上游 LibSass 弃用警告继续如实记录。

内链优先使用绝对站内路径，保留现有 slug、aliases 和外部可访问锚点。当前节页导航含相对 URL 且有精确字符串校验；修改时同时更新导航来源与校验，并检查渲染后的实际目标。不要把有效相对链接误当源码文件路径，也不要机械批量替换。

有用的引用紧随断言，删除纯修辞时保留支撑剩余事实的引用。重复或失效链接可以调整，质量标准是事实有出处、入口可到达，不是链接数量保持不变。

检查每个改动页面的生成输出和内链。浏览器抽查首页、目录、章首页、概念页、含长代码和表格的页面、Mermaid、事故操作页、英文入口及打印版；至少看桌面与窄屏。记录实际看过的样本，不能把抽样写成全站目视完成。

修改了 SQL 或实验脚本，运行与修改直接相关的检查；仅改文字不跑全套数据库演练。构建产物、下载文档、数据库与运行证据放在仓库外或已确认忽略的位置。不要把站点构建通过写成数据库实验通过。

### 12. 完成标准与汇报

完成需要同时满足：

- 每个在范围内的源文件都有完整阅读和去向记录，所有当前维护的稿件完成独立审阅。
- 保留的否定、警告、背景和总结都能回答删除判据；没有词频清零或凑字目标。
- 读者能从正文理解原因并采取下一步；补充的事实有来源，改动的技术行为有相应核验。
- 提纲、目录数据、生成模板和正文一致，下一次正常生成不会恢复被删掉的套话。
- 构建、链接和实际渲染检查通过；未核实内容、未执行实验和缺失版本单独列明。

最终汇报简洁给出处理文件数、各版本状态、几个典型前后对照、实际验证结果和遗留事项。缩短了多少只作参考，不能据此证明改好。

本任务默认交付可审阅的本地修改。不自动提交、推送、部署，不宣称网站已更新。完成全部已授权工作后再汇报。

### 13. 用本库例子校准尺度

下面只是表达示范；涉及技术细节的最终稿仍按上述流程核实。

**例一：去掉无关的否定。**

原句：

> 这样做的价值不是让一个玩具应用假装覆盖所有生产场景，而是让前一章的决定成为后一章可检查的输入。

改为：

> 各章沿用前面建立的数据、配置和工作负载，逐步加入查询优化、并发控制、部署和恢复实验。

**例二：从动作说明进入概念。**

原句：

> 一条连接字符串表达的是客户端的连接意图，不是服务器的自我证明。……可靠的第一步不是看到提示符就开始执行……

改为：

> 连接数据库后，先查询当前数据库、角色和后端地址，确认操作目标。连接串中的主机和端口可能指向代理，查询结果可以帮助你确认实际连接到了哪个 PostgreSQL 实例。

后面直接给已有 SQL，并解释查询列。密码处理、`search_path` 和角色切换等实际问题在各自相关位置讲清楚。

**例三：保留具体技术限制。**

原句：

> 通过 Unix socket 连接时，`inet_server_addr()` 和 `inet_server_port()` 会是 `NULL`，这不是故障。

可以改为：

> 通过 Unix socket 连接时，这两个函数返回 `NULL`；通过 TCP 连接时返回后端地址和端口。

保留了读者解释输出所需的信息。没有必要补一句“不能据此认为数据库异常”。

**例四：把章节任务写成人能理解的问题。**

原句：

> 在明确的失败模型、提交语义与权限边界内，系统能否维持一条被授权的可写历史，并在规定时间内把客户端带回可判断的服务状态？

改写方向：

> 主库故障后，哪台备库可以接管？哪些已提交的数据可能丢失？怎样阻止旧主库继续写入，让应用连到新主库？本章从这些问题解释复制、选主和切换。

随后分别解释必要机制。实验实际只覆盖计划切换时，在实验范围中明确说明；不能让读者误以为本章已经实测全部故障场景。

**例五：把必要警告落实为条件与后果。**

“不要轻率执行”“不能直接照搬到生产”“必须充分评估风险”本身没有帮助。对具体命令应交代会改变哪些数据或服务、执行前需满足什么条件、失败时在哪里停止、能否恢复。没有这些信息就补查，已有就删掉重复训话。
