连上数据库后，先确认三件事：当前在哪个数据库、以哪个角色登录、实际落在哪个 PostgreSQL 实例上。连接串里的主机可能经过 DNS 或 VIP，端口可能属于代理，登录角色还可能在会话内切换——这些都要用服务器端的查询结果来确认。本节给出确认方法。

本节全部操作属于 `R0·观察`。请使用第 0 章提供的实验凭据，密码不要写入命令历史、书稿或 Git。`pg36_shop` 尚未创建，因此先用 Pigsty L1 已有的管理数据库观察；将 `<L1_HOST>` 替换为实际域名或 IP：

```bash
export PG36_BOOTSTRAP_URL='postgresql://dbuser_dba@<L1_HOST>:5436/postgres?application_name=pg36-ch01'
psql -X "$PG36_BOOTSTRAP_URL"
```

`-X` 表示暂不读取个人 `psqlrc`，避免本地定制改变示例行为。安全保存凭据、服务文件和连接保护会在 ch02《psql 与可复现工作流》中展开。

## 1.1.1 主机、端口、服务、数据库与角色 {#item-1-1-1}

全书最终交给应用的是类似下面的 URI。先看懂它的每一段：

```text
postgresql://pg36_app@pg-meta:5433/pg36_shop?application_name=pg36-ch01
             └──角色──┘ └主机─┘└端口┘└─数据库──┘ └────连接参数─────┘
```

| 部分 | 它回答的问题 | 由谁解释 | 注意 |
|---|---|---|---|
| `pg-meta` | 客户端先去哪里建立网络连接？ | 客户端 DNS、`/etc/hosts`、Unix socket 或地址列表 | 可能是 VIP 或代理；最终落到哪个 PostgreSQL 实例，要用服务端查询确认 |
| `5433` | 目标主机上的哪个 TCP 入口？ | 监听该端口的进程或代理 | 在 Pigsty 中通常是 HAProxy 读写服务，而不是 PostgreSQL 本身（PostgreSQL 常见默认端口是 `5432`） |
| `pg36_shop` | 认证成功后进入哪个数据库？ | PostgreSQL | 数据库、模式、实例、集群是四个概念，区别见 1.2 |
| `pg36_app` | 以哪个数据库角色发起认证？ | PostgreSQL 认证规则 | 数据库角色与 Linux 用户无关，也不决定对象所有权 |
| `application_name` | 这条连接在活动视图和日志中叫什么？ | 客户端传入，PostgreSQL 记录 | 客户端可任意填写，用于区分连接来源，不能当作安全身份 |
{.wide .expand}

URI 支持 `postgresql://` 和 `postgres://` 两种 scheme。用户名、密码或数据库名含有 `@`、`:`、`/`、`?`、`#` 等保留字符时必须百分号编码。密码不要写进 URI——shell 历史、进程列表和日志都可能记录它；本章让 `psql` 交互式询问密码。

主机和端口组合成一个服务入口。Pigsty 的 `pg-meta:5433` 是读写服务：经 HAProxy 路由到当前主库；同一主机的 `pg-meta:5432` 通常直连当前 VIP 所在节点的 PostgreSQL。端口不同，到达路径与故障切换时的行为就不同，1.1.3 会把这套端点语义展开。

连接成功后，先执行一份上下文快照：

```sql
SELECT
    version()                         AS server_version,
    current_database()               AS database_name,
    session_user                     AS session_user,
    current_user                     AS current_user,
    inet_server_addr()                AS server_addr,
    inet_server_port()                AS server_port,
    pg_backend_pid()                  AS backend_pid,
    pg_is_in_recovery()               AS in_recovery;
```

每一列分别证明什么：

- `version()` 报告服务端的版本与构建信息；拿它和本机 `psql --version` 对比，可以确认客户端与服务器是否来自不同安装；
- `inet_server_addr()` 和 `inet_server_port()` 是 PostgreSQL 后端实际接受连接的地址与端口，正好用来核实代理路径：直连入口（如 `5436`、实例的 `5432`）返回实例地址与端口，端口值与客户端连接的入口不同；经 PgBouncer 的入口（如 `5433`）在 Pigsty 默认配置下返回 `NULL`，因为 PgBouncer 到 PostgreSQL 走 Unix socket；
- 通过 Unix socket 连接时，这两个函数返回 `NULL`；通过 TCP 连接时返回后端地址和端口；
- `pg_backend_pid()` 是当前 PostgreSQL 后端进程号，只在本次实例生命周期内有意义，可用于在日志和 `pg_terminate_backend()` 中定位这条连接；
- `pg_is_in_recovery()` 为 `false` 时实例不在恢复状态、通常可写（能否真正写入还要结合 1.1.3 的事务只读与权限查询确认），为 `true` 时处于恢复或热备状态。它只描述当前实例；整个复制链路的健康要用 `pg_stat_replication` 等证据判断（见第 20 章）。

把 URI 和这份快照放在一起，才是一份完整的落点记录：URI 说明你从哪个入口进来，快照说明服务器认为你在哪里。排障时两者都要在。

## 1.1.2 `current_database()`、`current_user` 与 `search_path` {#item-1-1-2}

进入服务器以后，还要确认三个会直接改变 SQL 含义的上下文：当前数据库、当前角色与模式搜索路径。

```sql
SELECT
    current_database()       AS database_name,
    session_user             AS authenticated_as,
    current_user             AS effective_as,
    current_setting('search_path') AS configured_path,
    current_schemas(true)    AS effective_path;
```

`current_database()` 返回当前连接所在数据库。PostgreSQL 会话一次只连接一个数据库；`\c` 看似在会话内“切库”，实际是 `psql` 断开后重新建立连接。跨数据库访问也没有 MySQL 那种 `db.table` 限定写法，需要 dblink、postgres_fdw 这类扩展。

`session_user` 是最初通过认证的角色，在连接期间通常保持不变（superuser 可用 `SET SESSION AUTHORIZATION` 改变它）；`current_user` 是当前权限检查使用的有效角色。执行 `SET ROLE` 或进入 `SECURITY DEFINER` 函数时，两者可能不同：

```sql
SELECT session_user, current_user;
-- 只有在当前角色有权切换时才能执行：
SET ROLE pg36_owner;
SELECT session_user, current_user;
RESET ROLE;
```

审计“谁连进来”时看 `session_user`，判断“当前 SQL 以谁的权限运行”时看 `current_user`。两者都是数据库角色，与操作系统账号无关。

`search_path` 决定没有写模式限定符的对象名如何解析，也决定未显式指定模式时新对象创建在哪里。假设有效路径是：

```text
pg_catalog, shop
```

那么系统对象优先从 `pg_catalog` 解析，业务对象再从 `shop` 查找。`current_setting('search_path')` 返回配置文本；`current_schemas(true)` 返回去除不存在或不可访问项后的有效路径，并按参数决定是否包含隐含的系统模式。

`search_path` 同时是安全边界：如果不可信用户能在搜索路径靠前的模式中创建对象，未限定名称的函数或操作符就可能解析到攻击者提供的对象。安全敏感的 SQL 应显式写出模式名，例如 `pg_catalog.set_config(...)` 或 `shop.orders`；应用与迁移脚本应使用受控路径。

本书为运行角色约定：

```sql
ALTER ROLE pg36_app IN DATABASE pg36_shop
SET search_path = pg_catalog, shop;
```

这条语句是 `R1·可逆变更`，只对角色 `pg36_app` 连接数据库 `pg36_shop` 时生效。回退方法是：

```sql
ALTER ROLE pg36_app IN DATABASE pg36_shop RESET search_path;
```

执行位置、权限与对象创建将在 1.7 一并处理。

## 1.1.3 实例端点、服务端点与只读端点 {#item-1-1-3}

端点可以指向固定实例，也可以表达一种稳定服务意图。两者都能建立连接，但承诺不同。

| 入口类型 | Pigsty v4.5 默认示例 | 典型路径 | 适合做什么 | 隐含假设 |
|---|---|---|---|---|
| PostgreSQL 实例直连 | `pg-meta-1:5432` | 客户端 → PostgreSQL | 本地管理、精确诊断单一实例 | 实例身份不会自动随故障切换变化 |
| PgBouncer 实例直连 | `pg-meta-1:6432` | 客户端 → PgBouncer → PostgreSQL | 精确访问某实例上的连接池 | 仍绑定固定实例 |
| primary 服务 | `pg-meta:5433` | 客户端 → HAProxy → 主库 PgBouncer → PostgreSQL | 应用读写 | 平台会根据当前角色路由到主库 |
| replica 服务 | `pg-meta:5434` | 客户端 → HAProxy → 备库 PgBouncer → PostgreSQL | 可容忍复制延迟的读取 | 没有合格备库时可能按配置回退 |
| default 服务 | `pg-meta:5436` | 客户端 → HAProxy → 主库 PostgreSQL | 管理、迁移、需要会话语义的直连 | 绕过连接池，但仍跟随主库 |
{.wide .expand}

这些是 Pigsty 的默认配置，用户可以修改。`5432` 才是 PostgreSQL 常见默认端口，`6432` 是 PgBouncer 常见默认端口。

服务名里的 replica 表达的是路由策略：把连接路由到一台备库。它不是数据库层的只读强制——写权限由角色授权、事务只读属性和数据库策略共同决定。单节点 L1 没有专用备库，replica 服务可能没有可用后端，或按配置回退到主库；即使连上了备库，下次故障切换也可能换一台机器承载。判断当前连接能否写入，用下面的查询，而不是看服务名。

```sql
SELECT
    pg_is_in_recovery()                    AS in_recovery,
    current_setting('transaction_read_only')::boolean AS transaction_read_only,
    has_database_privilege(
        current_user,
        current_database(),
        'CREATE'
    )                                     AS can_create_in_database;
```

三个结果回答三个不同的问题：实例是否在恢复、当前事务是否只读、角色是否拥有数据库级 `CREATE` 权限。写入能力还可能被表级权限、行级安全策略、函数权限和对象所有权改变，`has_database_privilege` 只是第一层。

### 一个两端互证练习

分别通过实例直连与 primary 服务建立连接，运行相同快照，并对比客户端入口与后端证据：

```bash
export PG36_INSTANCE_URL='postgresql://dbuser_dba@<INSTANCE_HOST>:5432/postgres?application_name=pg36-ch01-instance'
export PG36_PRIMARY_URL='postgresql://dbuser_dba@<L1_HOST>:5433/postgres?application_name=pg36-ch01-primary'

psql -X "$PG36_INSTANCE_URL" -c \
  "SELECT inet_server_addr(), inet_server_port(), pg_backend_pid(), pg_is_in_recovery();"

psql -X "$PG36_PRIMARY_URL" -c \
  "SELECT inet_server_addr(), inet_server_port(), pg_backend_pid(), pg_is_in_recovery();"
```

在单节点环境中，两次查询可能落到同一个 PostgreSQL 实例，但路径不同；在高可用环境中，primary 服务跟随主库角色变化，固定实例端点始终指向同一台机器。把两次实际结果都写进环境清单——结果与书中不同，恰好说明你的环境不同。
