本节把前五节的方法合成一次可重放的演练。它同时要求：

- 恢复目标由 source 上的独立审计记录导出，脚本里没有写死的 XID 或时间；
- 包含误操作的候选必须证明“误操作仍在”并被否决；
- 排除误操作的候选必须证明“误操作已消失”并被接受；
- 直接采用排除候选必须暴露“目标之后的合法写丢失”；
- 对账必须保住每一笔有审计记录的合法写；
- 全部清理与安全声明要经受对抗性篡改检查。

演练会创建并删除一次性 synthetic schema，创建两个 side-restore 目录后精确删除，并保留一份新全量备份。它只适用于已经确认的开发沙箱；确认字符串只保护这次实验，不构成生产授权。

## 32.6.1 在隐藏时间窗内注入误更新 {#item-32-6-1}

### 先读四份约定文件

- 环境、fixture 与验收：
  [`requirements.json`](/labs/ch32/requirements.json)
- 状态机、允许与禁止动作：
  [`recovery-contract.json`](/labs/ch32/recovery-contract.json)
- 人类可读安全边界：
  [`lab-contract.md`](/labs/ch32/lab-contract.md)
- 拓扑与数据流：
  [`topology.mmd`](/labs/ch32/topology.mmd)

静态检查不连接远端：

```bash
static/labs/ch32/task.sh lint
```

只读预检可在独立的新目录运行：

```bash
export PG36_EVIDENCE_DIR="$(
  mktemp -d "${TMPDIR:-/tmp}/pg36-ch32-capture.XXXXXX"
)"
static/labs/ch32/task.sh capture
```

它验证：

```text
target 身份与三成员 Patroni 拓扑
pg-test-1 是唯一运行中的主库
pg-test-2/3 处于流复制状态
PostgreSQL 主版本与 cluster_name
fixture schema 尚不存在
恢复前缀目录为空、端口空闲
备份仓库可读
Pig pitr 所需标志齐全
source 与 upstream 证据哈希
```

`capture` 不改动任何远端状态：不创建备份，不建恢复目录，也不动 Patroni、DCS 或路由。

### 完整演练

完整演练在新的私有证据目录中进行：

```bash
export PG36_EVIDENCE_DIR="$(
  mktemp -d "${TMPDIR:-/tmp}/pg36-ch32.XXXXXX"
)"
export PG36_CH32_TARGET=pg36-l2-vagrant/pg-test
export PG36_CH32_NONPRODUCTION=true
export PG36_CH32_PRODUCTION_DATA=false
export PG36_CH32_PRODUCTION_TRAFFIC=false
export PG36_CH32_CONFIRM=RANDOM_XID_PITR_RECONCILE_CH32

static/labs/ch32/task.sh drill:pitr
```

任一保护变量（guard，即上面的 `PG36_CH32_*` 五个变量）缺失，runner 在改动 source 之前退出；证据目录已非空也会退出，避免把新 run 混进旧证据。正式实现见：

- [`capture.py`](/labs/ch32/capture.py)
- [`exercise.py`](/labs/ch32/exercise.py)
- [`validate.py`](/labs/ch32/validate.py)
- [`review.py`](/labs/ch32/review.py)
- [`task.sh`](/labs/ch32/task.sh)

### fixture 是一份可独立计算的账

`test.pg36_ch32` 有 5,000 个账户：

```text
account_id       1 .. 5000
opening balance  100000 + account_id cents
status           active
```

opening total：

$$
5000 \times 100000
+ \frac{5000 \times 5001}{2}
=512{,}502{,}500
$$

runner 用系统随机源选择连续 1,000 个 victim。目标账户范围、run ID 与事故时刻只在本次私有证据中确定，恢复命令没有预置 XID 或固定时间。

### 四笔事务和一份新备份

顺序：

```text
base 事务
  创建 5,000 个账户和运行标记
  写入 base 审计

新的全量备份

safe-before 事务
  给全部 1,000 个 victim 账户 +100 分
  插入 1,000 条 safe 账目
  写入 safe XID 审计

damage 事务
  把 1,000 个 victim 余额清零
  status 改为 mispriced
  创建 1,000 条 fixture 专用 pending outbox 行
  同一事务写入 damage XID 审计

post-target 事务
  给前 100 个 victim +700 分
  插入 100 条合法账目
  写入 post-target XID 审计
```

damage 和 outbox 在同一事务里提交，因此 inclusive 候选要么同时看到两者，要么实验判定失败。fixture 没有外部 dispatcher，`external_dispatch_enabled=false` 同时写进审计与约定文件。

注意 source 在 damage 后、修补前的当前值：

```text
first 100 victims    balance=700, status=mispriced
other 900 victims   balance=0,   status=mispriced
```

而正确历史值应是 opening + 100，前 100 个账户还要再加合法的 700。这个设计让“把恢复值直接写回”必然丢数据，操作者必须处理目标之后的合法写（good-after）。

### 恢复目标从 source 审计导出

runner 在三笔事务完成后，单独查询：

```text
pg36_ch32.incident_audit
  where run_id = exact marker
    and stage = damage
```

取得 damage XID，再记录当前 LSN 与所需的 WAL segment。随后执行一次 WAL switch、`pgbackrest check`，轮询 repository 直到 archive max 覆盖所需 segment。若 XID 缺失、不是数字、与 damage 事务返回值不一致，或归档尚未覆盖，恢复不会开始。

这里的要点是方法本身：恢复目标的身份要从独立于恢复流程的事实导出，并与业务身份绑定。生产中承担这一角色的是你自己的审计机制，表名不必相同。

## 32.6.2 独立定位目标、恢复、验证与回切 {#item-32-6-2}

本节恢复出两个候选、验证并选出正确的一个，最后把恢复数据合并回 source。这里的“回切”指数据合并，不是应用切流。

### 两个候选只差一个变量

| 参数 | inclusive | exclusive |
|---|---|---|
| backup | 同一 exact fresh full | 同一 exact fresh full |
| target | 同一 damage XID | 同一 damage XID |
| timeline | `current` | `current` |
| action | `promote` | `promote` |
| side directory | marker/inclusive | marker/exclusive |
| archive mode | `off` | `off` |
| 差异 | 默认 inclusive | `--exclusive` |

两个 plan 都先被保存和校验。两个 postmaster 顺序启动在同一空闲端口，只监听各自 mode-0700 Unix socket；inclusive 停止并删除后才创建 exclusive。

### inclusive 候选必须被否决

正式 run 观察：

```text
base 审计                    存在
safe-before 审计             存在
safe 账目                    1,000 条
目标 XID 的 damage 审计      存在
mispriced 的 victim 行       1,000 行
pending 的错误 outbox        1,000 条
post-target 审计/账目        缺失 / 0
decision                     rejected
```

这证明默认的 inclusive XID 语义停在目标事务之后。如果 validator 只检查 `pig_result.success` 而不检查数据，这个错误候选会显得完全健康。

### exclusive 候选才是历史正确边界

```text
base 审计                    存在
safe-before 审计             存在
safe 账目                    1,000 条
damage 审计                  缺失
pending 的错误 outbox        0 条
post-target 审计/账目        缺失 / 0
victims active               1,000
victim 余额合计              确定的 opening + 100 each
decision                     accepted
```

source timeline 为 11；两个隔离候选沿 `current` 重放并 promote 到 timeline 12。`archive_mode=off` 使两个实验分支不会进入共享 repository。

accepted 只表示该候选可作为历史正确的数据源；它还缺 100 笔目标之后的合法账目，要靠本节后面的对账步骤补齐，因此不能直接切流。

### 从候选提取，再与 source 审计合并

exclusive candidate 导出 1,000 行：

```text
account_id
recovered_balance_cents
status=active
```

私有证据只保存导出行数和导出集合的 SHA-256。source 独立导出 100 条 `post-target` ledger，要求 key 集合恰好等于预期的 100 个账户，每条 delta 都是 700。

runner 构造 typed temporary table：

```text
account_id
recovered_balance_cents
post_delta_cents
expected_current_balance_cents
```

一笔事务中先验证 1,000 行 current preimage：

```text
前 100 个账户的期望当前余额 = 700
其余 900 个账户            = 0
全部 status = mispriced
```

完全匹配后才执行：

```text
新余额 = 恢复余额 + 审计的 post 增量
status = active
pending 错误 outbox -> canceled
```

条件更新或 outbox 行数不是 1,000 时，事务抛错并回滚。

### 最终 manifest 独立可算

safe 增量：

$$
1000 \times 100 = 100{,}000
$$

post-target 合法增量：

$$
100 \times 700 = 70{,}000
$$

最终总额：

$$
512{,}502{,}500 + 100{,}000 + 70{,}000
=512{,}672{,}500
$$

正式结果：

```text
accounts                    5,000
total balance               512,672,500 cents
victims active              1,000
victims mispriced           0
safe ledger                 1,000
post-target ledger          100
pending wrong outbox        0
canceled wrong outbox       1,000
external dispatch           0
```

runner 最后按 exact run marker 删除 `pg36_ch32`，停止两个 candidate，确认 socket/PID 消失后删除两个恢复根目录（exact roots）；再次验证 Patroni 仍为一主两从、source system lineage 未变、fresh backup 仍在 repository。整个演练不执行应用切流。

## 32.6.3 测量 RPO/RTO 并记录版本迁移工时 {#item-32-6-3}

### 正式时间分解

公开证据
[`pitr-run.json`](/labs/ch32/pitr-run.json) 记录：

| 阶段 | inclusive | exclusive |
|---|---:|---:|
| plan | 0.219 s | 0.214 s |
| restore copy | 3.040 s | 2.974 s |
| start → promoted | 0.961 s | 0.939 s |
| candidate validation | 0.340 s | 0.503 s |

共同阶段：

```text
target identification        0.183 s
fresh full backup            2.090 s
pgBackRest check             0.630 s
reconciliation               0.200 s
backup logical size          42,355,954 bytes
repository delta              5,751,304 bytes
```

这是本地 ARM64 四虚拟机、42.4 MB 合成数据的一次观测。磁盘缓存、已有 repository、网络距离、压缩/加密、WAL 数量、表空间、extension 和并发都与生产不同。

### 一次事故有多种 RPO

| 口径 | 本次结果 | 含义 |
|---|---:|---|
| archive RPO | target WAL covered | 没有注入 WAL 缺口 |
| raw exclusive loss | 100 rows | 为排除 damage，故意丢弃 target 后合法写 |
| reconciled fixture loss | 0 rows | 100 条 audited delta 全部合并 |
| external-system loss | 未测试 | 没有真实 payment/message provider |
{.wide .expand}

因此结论要写完整：

> 在这份 synthetic fixture、完整 audit 与无外部 dispatch 的条件下，exclusive PITR 原始缺少 100 笔合法写；经过条件对账后，已知 fixture 数据损失为 0。

生产中没有完整的 good-after 审计时，对账后的 RPO 是未知——WAL 完整本身不会把它变成 0。

### restore time 不是 RTO

本次没有测量：

```text
事件检测
人工目标调查
生产审批
大规模验证
业务方对账
应用部署/配置变更
连接池排空与切流
缓存/搜索重建
观察窗口
```

因此公开证据固定：

```text
timings_are_sandbox_observations = true
production_rto_claimed = false
```

生产演练应测端到端：

```text
t0 宣布事件
t1 停止变更（mutation fenced）
t2 批准恢复目标
t3 候选实例就绪
t4 候选通过业务验证
t5 good-after/外部对账完成
t6 业务流量恢复
t7 观察窗口结束
```

分别报告各阶段时长与关键路径，而不是只取最快的 `restore copy`。

### 版本恢复与版本迁移是两项工时

物理 backup 要由兼容的 PostgreSQL major 与 extension library 启动。若事故时生产已经升级，而目标 backup 属于旧 major，runbook 可能需要：

```text
取得精确的旧版 server 二进制
取得配套的 extension 库
重建 locale/collation 运行时
在旧 major 上恢复并验证
导出选定数据
转换并导入当前 major
验证跨版本语义
```

这段工时要独立记录，不能用“目标主机已经装了新版 PG”抵消。PG18 的 server 不能直接启动 PG17 的 PGDATA；跨 major 迁移应走第 30 章的 `pg_upgrade`、逻辑迁移或对象提取路径。

本次 source、backup 与 candidate 使用同一 PostgreSQL 版本（正式证据记录为 18.4，见
[`pitr-run.json`](/labs/ch32/pitr-run.json)，早于本书复现基线 18.6），没有执行跨
major 迁移。本次只证明“同 major 运行时已就绪”的恢复路径，跨版本迁移工时未测得；
生产报告应写 `not required in this scenario`，而不是记 0 秒。

建议工时表：

| 工作 | 开始 | 结束 | 有效工时 | 等待 | 负责人 | 证据 |
|---|---|---|---:|---:|---|---|
| old runtime acquire | | | | | | |
| extension compatibility | | | | | | |
| physical restore | | | | | | |
| logical extract/transform | | | | | | |
| target import | | | | | | |
| cross-version validation | | | | | | |
{.wide .expand}

## 32.6.4 输出恢复证据和备份体系改进项 {#item-32-6-4}

### 私有证据包

```text
preflight-evidence.json
exercise-manifest.json
source-before.json
fixture.json
backup.json
inclusive-plan.json
inclusive-recovery.json
exclusive-plan.json
exclusive-recovery.json
reconciliation.json
source-after.json
cleanup.json
negative-report.json
validation-report.json
public-summary.json
review.txt
```

目录权限 `0700`，文件权限 `0600`。review 拒绝 SCRAM verifier、private key、明文密码、credential URI 和 raw system identifier。公开摘要只保留版本、规模、计数、时间、候选决策与安全结论。

对完成的同一证据目录，可以离线重跑：

```bash
export PG36_EVIDENCE_DIR=/private/existing/ch32-run
static/labs/ch32/task.sh verify
static/labs/ch32/task.sh review
```

`all` 也只执行 verify + review，不会再次创建 fixture、backup 或 restore。修改 12 个实验源文件中的任何一个后，旧 preflight/source hash 会失败；这时应开启新 run，旧证据不能重新盖章。

### 32 个反例

validator 把每份完整证据深拷贝后注入变异，全部 32 项都必须被拒绝。以下为主要类别：

```text
授权类：
  允许生产数据
  允许改动托管 PGDATA / Patroni
  允许备份过期

目标类：
  用时间替换审计 XID
  禁用 exclusive
  timeline 改为 latest
  打开 archive mode
  打开 TCP 监听

预检类：
  target/主库/拓扑改变
  source 或 upstream 哈希改变

恢复类：
  damage XID 或 backup label 改变
  归档覆盖为假
  inclusive 候选 damage 缺失，或被标记为 accepted
  exclusive 候选含 damage / 含 post / 缺 safe

对账类：
  修复行数 = 999
  post-target 写丢失
  external dispatch = 1

清理/治理类：
  路由改变
  恢复目录残留
  生产 gate 被批准
```

正式 run：

```text
declared counterexamples rejected  32 / 32
live evidence mutants rejected     32 / 32
source files hash-bound            12 / 12
secret material                    absent
```

### 从一次成功演练生成改进 backlog

按发现分类：

| 类别 | 本次证明 | 下一轮故意测试 |
|---|---|---|
| target | exact serial damage XID | 并发事务与宽时间窗 |
| WAL | target 后 segment 已归档 | 缺一个 WAL、archive 延迟、坏 history |
| repository | 单一 sandbox repo 可读 | lost key、read-only credential、immutable/off-site |
| backup | fresh full | diff/incr dependency 与过期边界 |
| runtime | 同 PG18.4（本书基线 18.6） | 旧 major、缺 extension、collation drift |
| data | 5,000 确定性账户 | 多 TB、tablespace、large object |
| reconcile | 100 audited deltas | 冲突写、未知 delta、人工 exception |
| side effects | fixture dispatcher absent | broker/payment/search sandbox |
| topology | source HA 未变 | 经授权的 managed restore/rejoin |
| service | 未切流 | application smoke、pool drain、观察窗 |
{.wide .expand}

每项改进要有负责人、截止时间、下次演练场景和通过证据。

### 这次演练证明了什么

本章正式证据支持：

```text
按审计 XID 精确定位恢复目标
inclusive / exclusive 边界行为符合定义
隔离的 Pig side restore
post-target 对账
fixture 与恢复目录的精确清理
source HA 拓扑保持不变
```

它不覆盖：

```text
生产切流
最坏情况下的归档 RPO
生产 RTO
外部副作用补偿
跨 major 恢复
区域级灾难恢复
```

这些缺口需要各自的授权与演练：切流与外部副作用属于业务演练，跨 major 恢复属于第 30 章的升级预案，区域级灾难恢复需要第二个机房。

下一章转向另一种故障：数据本身正确，但写入者、timeline 或节点拓扑失去了唯一性——主从切换、fencing、`pg_rewind` 与故障节点重建。
