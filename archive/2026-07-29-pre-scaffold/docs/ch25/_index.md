## 1) 章节定位（一句话）
把 `ch24` 的治理目标（`SLA/SLO/SLI/SOP/RACI`）落成一套可执行、可验收的数据库可观测性体系，用于故障预防与快速定位，并产出 `ch26` 容量规划输入。

## 2) 学习完成标准（3-5 条，必须可验证）
1. 产出 `docs/ch25/01_observe_contract.yaml`，至少覆盖主线 `paydb` 与支线 `reportdb`，且每条 `SLI` 都有 `metric/threshold/window/owner`（字段完整率 `100%`）。  
2. 产出 `docs/ch25/02_metric_catalog.yaml`，至少包含 `可用性/延迟/错误率` 三类指标，并标注采样周期与数据来源。  
3. 产出 `monitoring/rules/paydb_observe_rules.yml`，规则文件通过 `promtool check rules` 校验。  
4. 完成一次定位演练：从告警触发到定位结论（含证据）总耗时 `<=15` 分钟，并形成 `artifacts/ch25/diagnose_drill.md`。  
5. 产出 `docs/ch25/ch26_input.yaml`，至少包含 `peak_qps/peak_conn/p95_latency/daily_growth_gb` 四项容量前导指标。  

## 3) 章节边界
- 本章要讲什么（5-7 条）
1. 如何把 `ch24` 的治理输入转成可观测实施清单。

5. 如何执行“望闻问切”定位路径，缩短诊断收敛时间。

## 5) 实战实验设计
- 实验 A（基础）：目标、前置条件、步骤、验收标准  
目标：搭建 `paydb` 的最小可观测闭环，并验证“可测、可告、可定位”。  
前置条件：`docs/ch24/ch25_input.yaml` 已就绪；PostgreSQL 与监控组件可访问；有 `paydb` 查询权限。  
步骤：  
1. 从 `ch24` 输入生成 `01_observe_contract.yaml`。  
2. 建立三类核心指标（可用性、延迟、错误率）与基线。  
3. 校验采集链路健康状态（target 为 `up`）。  
4. 应用规则文件并触发一次测试告警。  
5. 记录一次告警恢复闭环。  
验收标准：  
1. 观测契约至少 `3` 条 SLI 且字段完整。  
2. `paydb` 指标在最近 `15` 分钟无采集断点。  
3. 告警在触发后 `<=2` 分钟出现，恢复后 `<=5` 分钟清除。  
4. 演练日志包含时间戳、执行人、证据链接三要素。  

- 实验 B（进阶）：目标、前置条件、步骤、验收标准  
目标：用可观测性完成一次“预防+定位”演练，并输出 `ch26` 容量输入。  
前置条件：实验 A 通过；已有近 `7` 天指标数据；主线责任人已确认。  
步骤：  
1. 使用 `pgbench` 注入 10 分钟突发负载（连接与 TPS 上升）。  
2. 观察预警与严重告警触发先后。  
3. 按“望闻问切”路径在 15 分钟内给出瓶颈结论。  
4. 抽取峰值 QPS、峰值连接、P95 延迟、日增量存储。  
5. 写入 `docs/ch25/ch26_input.yaml`。  
验收标准：  
1. 预警告警先于严重告警触发，时间差 `>=5` 分钟。  
2. 定位结论至少由 `3` 条证据支撑（指标/日志/SQL 观测）。  
3. 从首条告警到定位结论 `<=15` 分钟。  
4. `ch26_input.yaml` 四项容量前导指标齐全且有时间窗口。  

## 6) 常见误区与纠偏（5 条）
1. 误区：只做大盘，不做责任绑定。纠偏：每条关键指标必须有 `owner`。  
2. 误区：阈值照抄模板。纠偏：先采样基线，再设预警与严重阈值。  
3. 误区：只测告警触发，不测恢复清除。纠偏：每条规则都做“触发+恢复”双向验证。  
4. 误区：定位靠经验聊天。纠偏：统一使用“症状-证据-结论”记录模板。  
5. 误区：观测数据不用于容量规划。纠偏：每周固定输出容量前导指标到 `ch26` 输入。
