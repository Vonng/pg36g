## 1) 章节定位（一句话）
承接 `ch31` 事件输入，建立一套可重复执行、可验收的 `PITR + 误操作恢复` 标准演练流程，在不进入故障切换重建的前提下把业务恢复到可用状态。

## 2) 学习完成标准（3-5 条，必须可验证）
1. 能基于 `docs/ch31/ch32_input.yaml` 在 `15` 分钟内完成恢复触发判断与恢复目标点确定。
2. 完成 1 次主线 `PITR` 演练，恢复目标时间偏差不超过 `60` 秒。
3. 完成主线误操作恢复后，至少 `6` 条一致性校验 SQL 全部通过（通过率 `100%`）。
4. 完成 1 次支线单表误删恢复演练，表结构与行数校验一致率 `100%`。
5. 产出 `docs/ch32/ch33_input.yaml`，字段完整率 `100%`，并明确是否需要升级到 `ch33`。

## 5) 实战实验设计
实验 A（基础）  
目标：完成一次标准 PITR（隔离环境）并形成可验证恢复报告。  
前置条件：存在完整基线备份 + 连续 WAL；`docs/ch31/ch32_input.yaml` 已就绪；有独立恢复主机。  
步骤：  
1. 读取 `ch31` 输入并冻结现场。  
2. 通过审计日志确定误操作窗口与恢复目标时间。  
3. 执行 `pgbackrest restore --type=time --target='<ts>'` 并启动恢复实例。  
4. 执行 6 类一致性校验 SQL 并记录结果。  
验收标准：  
1. 恢复目标时间偏差 `<= 60` 秒。  
2. 恢复实例启动耗时 `<= 25` 分钟。  
3. 6 类校验 SQL 通过率 `100%`。  
4. `RPO` 实测 `<= 5` 分钟。  

实验 B（进阶）  
目标：完成主线误更新恢复 + 支线单表误删恢复，并给出是否进入 `ch33` 的量化判定。  
前置条件：实验 A 通过；可申请一次受控维护窗口；已有恢复与回灌脚本模板。  
步骤：  
1. 主线：按目标时间完成 PITR，导出并回灌 `app.orders` 正确数据。  
2. 支线：恢复 `app.coupon_usage` 结构与数据。  
3. 执行业务回归 SQL（订单状态、金额、优惠券核销链路）。  
4. 统计 `RPO/RTO` 并生成 `docs/ch32/ch33_input.yaml`。  
验收标准：  
1. 主线受影响行恢复数量与基线一致（偏差 `0`）。  
2. 支线表结构与行数比对一致率 `100%`。  
3. 业务回归 SQL 通过率 `100%`（不少于 `8` 条）。  
4. 端到端恢复总时长 `<= 90` 分钟。  
5. `ch33` 输入字段完整率 `100%`。  

## 6) 常见误区与纠偏（5 条）
1. 误区：恢复目标时间选在误操作之后。纠偏：必须先锁定“首条坏事务时间”，目标点取其前一安全点。  
2. 误区：未冻结写入就开始恢复。纠偏：先完成停写与日志保全检查项，再执行 PITR。  
3. 误区：只看 `count(*)` 就宣布恢复成功。纠偏：必须补做金额、状态分布、关键主键抽样等业务校验。  
4. 误区：在生产数据目录直接覆盖恢复。纠偏：一律先在隔离环境恢复，验证通过后再受控回灌。  
5. 误区：恢复完成但无升级判定。纠偏：必须输出 `RPO/RTO/残余风险`，明确是否进入 `ch33`。
