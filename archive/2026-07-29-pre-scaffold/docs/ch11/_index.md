## 1) 章节定位（一句话）
以 `wallet_txn` 新增 `request_id` 为主线，建立可落地的“预检-扩展-灰度-收缩-回滚-演练”模式变更发布闭环。

## 2) 学习完成标准（3-5 条，必须可验证）
1. 能在演练库按顺序执行 `00_precheck.sql -> 10_expand.sql -> 20_backfill.sql -> 30_contract.sql -> 40_accept.sql`，且全程无报错。  
2. 灰度阶段新旧版本并行 30 分钟，旧接口与新接口各 200 次请求成功率均为 100%。  
3. 验收 SQL 达标：`request_id` 空值数为 0、重复值数为 0。  
4. 任一回滚点触发后，10 分钟内恢复到可写状态，并通过同一套验收 SQL。  
5. 产出可复跑发布包：预检报告、变更脚本、回滚脚本、验收报告各 1 份。

## 5) 实战实验设计
实验 A（基础）  
目标：完成主线案例的“扩展->灰度->回填->收缩”闭环。  
前置条件：有 staging 库（建议 `wallet_txn` >= 10 万行），可控制发布开关。  
步骤：  
1. 运行 `00_precheck.sql`，确认可进入变更窗口。  
2. 执行 `10_expand.sql` 增加字段与索引。  
3. 发布新版本写路径，按 10%/50%/100% 灰度。  
4. 执行 `20_backfill.sql` 分批补齐历史 `request_id`。  
5. 执行 `30_contract.sql` 收紧约束。  
6. 执行 `40_accept.sql` 生成验收报告。  
验收标准：  
1. `SELECT count(*) FROM wallet_txn WHERE request_id IS NULL;` 返回 `0`。  
2. 重复检查返回 `0` 行：`GROUP BY request_id HAVING count(*)>1`。  
3. 灰度期间旧/新接口各 200 次请求全部成功。  
4. 变更期间无单次锁等待超过 5 秒。  

实验 B（进阶）  
目标：在压力下完成两类回滚演练并恢复发布。  
前置条件：实验 A 完成；具备并发压测入口（如 `pgbench`）。  
步骤：  
1. 启动持续流量：`pgbench -c 32 -T 600 -f sql/ch11/pay_api.sql`。  
2. 在回滚点#1 注入故障（新读路径异常），执行开关回退。  
3. 在回滚点#2 注入故障（约束触发失败），执行 `31_rollback_contract.sql`。  
4. 故障解除后重新执行 `30_contract.sql` 与 `40_accept.sql`。  
验收标准：  
1. 两次回滚都在 10 分钟内完成。  
2. 回滚后与重试后，空值数/重复值数仍为 0。  
3. 发布恢复后 15 分钟内错误率回到基线。  
4. 演练脚本可重复执行，结果一致。  

## 6) 常见误区与纠偏（5 条）
1. 误区：直接 `ADD COLUMN ... NOT NULL DEFAULT ...` 一步到位。纠偏：先加可空列，再回填，再收紧。  
2. 误区：一次性全表回填。纠偏：分批回填并实时看锁等待与耗时。  
3. 误区：新版本上线就立刻切新读路径。纠偏：先双写稳定，再切读。  
4. 误区：只有回滚脚本，没有回滚演练。纠偏：每个回滚点至少演练一次并记录时长。  
5. 误区：以“没报错”作为验收。纠偏：必须以 SQL 门禁（空值、重复、不变量）验收。
