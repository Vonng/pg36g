## 1) 章节定位（一句话）
在 `ch06` 评审产物基础上，本章教会读者用执行计划与统计视图快速锁定慢 SQL 线索，并产出可直接进入 `ch08` 的诊断证据包。

## 2) 学习完成标准（3-5 条，必须可验证）
- 能用 `pg_stat_statements` 拉出 Top10 候选 SQL，并明确 1 条主线 SQL（含 `queryid`、`calls`、`total_exec_time`）。  
- 能对主线 SQL 提交 1 份 `EXPLAIN (ANALYZE, BUFFERS)` 解读卡，标出最耗时节点与其实际行数。  
- 能计算至少 3 个关键节点的“估算偏差比（实际行数/估算行数）”，并标记阈值超限项（`>10`）。  
- 完成一次 `ANALYZE` 回归后，主线 SQL 平均耗时下降 `>=40%`，且结果行数一致。  
- 交付 4 份证据：候选 SQL 清单、计划对照表、偏差对照表、主线闭环报告。

- 用 `pg_stats` 对照估算偏差比，判断统计信息是否失真。

## 5) 实战实验设计
- 实验 A（基础）：目标、前置条件、步骤、验收标准  
目标：完成一次“统计视图选样本 -> 执行计划定位热点”的最小闭环。  
前置条件：已启用 `pg_stat_statements`；有 `orders/order_items/payments` 测试数据；可执行回放脚本。  
步骤：  
1. 回放业务 SQL 3-5 分钟。  
2. 查询 `pg_stat_statements`，锁定主线 SQL。  
3. 对主线 SQL 执行 3 次 `EXPLAIN (ANALYZE, BUFFERS)`。  
4. 计算关键节点估算偏差比并填写对照表。  
验收标准：  
1. 明确 1 条主线 SQL（含 `queryid`）。  
2. 明确 1 个热点节点（节点耗时占比 `>=40%`）。  
3. 给出至少 3 个节点偏差比。  
4. 交付 `ch07_clue_sheet.csv` 与 `ch07_plan_before.txt`。  

- 实验 B（进阶）：目标、前置条件、步骤、验收标准  
目标：验证“统计信息修复 + SQL 改写”是否真正改善计划与耗时。  
前置条件：实验 A 已完成；主线 SQL 存在偏差比超限（`>10`）。  
步骤：  
1. 记录基线：执行主线 SQL 5 次，保存平均耗时与计划。  
2. 执行 `ANALYZE orders,order_items,payments;`。  
3. 重跑 5 次并保存新计划。  
4. 若偏差仍高，改写一个低效谓词后再次对比。  
5. 汇总 before/after 证据并写出结论。  
验收标准：  
1. 主结果集一致（行数一致）。  
2. 热点节点偏差比从 `>10` 降到 `<=3`（或下降 `>=70%`）。  
3. 平均耗时下降 `>=40%`。  
4. 输出 `ch07_case_report.md`，含 1 条可进入 `ch08` 的诊断假设。  

## 6) 常见误区与纠偏（5 条）
1. 误区：只看 `cost` 不看实际执行。纠偏：必须使用 `EXPLAIN (ANALYZE, BUFFERS)`。  
2. 误区：只盯单次最慢。纠偏：先按 `total_exec_time` 排优先级。  
3. 误区：偏差大就直接加索引。纠偏：先核对 `pg_stats` 并做 `ANALYZE` 回归。  
4. 误区：看到顺序扫描就判错。纠偏：结合返回行数占比与实际耗时判断。  
5. 误区：优化后只跑一次就下结论。纠偏：固定脚本重复 5 次取平均并留存 before/after。
