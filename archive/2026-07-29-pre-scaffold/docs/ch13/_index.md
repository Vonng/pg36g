## 3) 章节边界
- 本章要讲什么（5-7 条）
1. 从 ch12 已上线服务提炼“能力缺口”，而不是从工具清单出发。  
2. 先筛内核分支，再筛扩展生态，形成候选路线。  
3. 用风险分级和退出策略控制技术债与回退成本。  
4. 用证据矩阵和基线测试验证候选路线可行性。  
5. 用统一验收门槛收敛为单一路线决策。  
6. 交付 ch14 所需输入（检索场景、数据样本、验收基线）。  
7. 首次术语控制为 12 个：`内核分支`、`扩展生态`、`能力缺口`、`兼容级别`、`生命周期`、`风险分级`、`证据矩阵`、`最小可行组合`、`基线测试`、`验收门槛`、`退出策略`、`变更窗口`。  

- 本章明确不讲什么（3-5 条）
1. 任一扩展的源码实现细节。  
2. 任一扩展/分支的部署手册大全。  
3. 厂商产品横评与“排行榜式”推荐。  
4. 全量运维治理（备份、容灾、故障切换）专题。

## 5) 实战实验设计
- 实验 A（基础）：目标、前置条件、步骤、验收标准  
目标：完成“缺口识别 -> 候选筛选 -> 证据验证 -> 决策收敛”的最小闭环。  
前置条件：已完成 ch12 交付；有可用 staging 库；可执行 `psql` 与 `pgbench`。  
步骤：  
1. 执行 `psql -f sql/ch13/01_gap_check.sql` 生成能力缺口。  
2. 执行分支与扩展清单采集命令，填充两张筛选表。  
3. 执行 `pgbench` 回放与 `05_accept.sql` 验收。  
4. 执行 `06_score.sql` 并产出决策记录。  
5. 打包 ch14 交付物。  
验收标准：  
1. `branch_filter.csv` 至少 2 条候选路线，且仅 1 条“通过”。  
2. `ext_combo.csv` 至少 2 组组合，评分字段完整率 100%。  
3. `accept_report.txt` 失败项为 `0`。  
4. 选定路线相对基线的 P95 延迟增幅 `<=20%`。  

- 实验 B（进阶）：目标、前置条件、步骤、验收标准  
目标：在约束变化下验证退出策略和变更窗口可执行。  
前置条件：实验 A 通过；已准备第二候选路线。  
步骤：  
1. 对已选路线执行一次完整基线测试。  
2. 注入约束变化（例如生命周期检查项不通过），标记当前路线失效。  
3. 按退出策略切换到第二候选路线并重跑 `06_score.sql`。  
4. 对第二路线执行 `replay.sql` 与 `05_accept.sql`。  
5. 更新决策记录与交接包。  
验收标准：  
1. 切换与恢复总时长 `<=15` 分钟。  
2. 切换后 `accept_report.txt` 失败项仍为 `0`。  
3. 切换后关键查询错误数为 `0`。  
4. `decision_record.md` 明确记录“触发条件-切换动作-恢复结果”。  

## 6) 常见误区与纠偏（5 条）
1. 误区：先看“热门扩展”，后补需求。纠偏：先做能力缺口，再建候选路线。  
2. 误区：只比性能。纠偏：兼容级别、生命周期、退出策略必须同权评估。  
3. 误区：分支和扩展分开决策。纠偏：按“分支 + 扩展组合”整体打分。  
4. 误区：验收只看压测结果。纠偏：必须同时通过 `05_accept.sql` 的正确性门槛。  
5. 误区：决策文档只写“选了什么”。纠偏：必须写“为什么不选其他方案”。
