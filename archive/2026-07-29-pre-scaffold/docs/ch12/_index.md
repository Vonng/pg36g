## 1) 章节定位（一句话）
以 ch11 已完成的 `request_id` 模式变更为起点，把数据库契约落地为可上线、可回滚、可验收的后端服务交付链路。

## 2) 学习完成标准（3-5 条，必须可验证）
1. 能执行 `make test-int`，并通过支付服务端到端集成测试（返回码为 0）。
2. 对同一 `request_id` 连续调用两次创建接口，数据库仅新增 1 条业务记录（`count(*)=1`）。
3. 能按 `10% -> 50% -> 100%` 完成灰度发布，每阶段 10 分钟内接口错误率 `<0.1%`。
4. 能执行 `psql -f sql/ch12/accept.sql`，并满足：空值/重复值检查均为 `0`。
5. 能产出 `ch12_delivery_pack`（接口契约、发布脚本、回滚脚本、验收报告各 1 份）。

## 3) 章节边界
- 本章要讲什么（5-7 条）
1. 将 ch11 的数据变更结果转成后端接口契约与验收门禁。
2. 用单条主线案例打通“写接口 -> 读接口 -> 发布 -> 回滚 -> 验收”。
3. 在写路径中落实幂等、事务边界、错误映射。
4. 在运行路径中落实连接池、超时、并发压测与观测基线。
5. 用可执行脚本完成灰度发布与回滚演练。
6. 为 ch13 准备扩展接口清单，不做生态横评。
7. 首次术语控制为 11 个：`服务契约`、`数据契约`、`幂等键`、`事务边界`、`错误映射`、`连接池`、`灰度发布`、`回滚点`、`观测基线`、`验收门禁`、`扩展接口`。

- 本章明确不讲什么（3-5 条）
1. 单一后端框架的完整教程（如某框架脚手架全流程）。
2. Supabase/云产品“全家桶”部署与组件百科。
3. PostgreSQL 扩展生态横评或选型排名。
4. 企业级 CI/CD 平台搭建细节与审批流实现。
5. 跨地域容灾、PITR、故障切换等运维专题。

## 5) 实战实验设计
- 实验 A（基础）
目标：完成支付服务“数据库到后端接口”的最小可交付闭环。  
前置条件：已完成 ch11 主线变更；本地可访问 PostgreSQL；具备服务启动脚本。  
步骤：  
1. 执行 `psql -f sql/ch11/40_accept.sql` 确认数据库契约可用。  
2. 启动服务：`make run`。  
3. 调用创建接口两次（同 `request_id`），再调用查询接口一次。  
4. 执行 `psql -f sql/ch12/accept.sql`。  
5. 生成交付包：`make pack-ch12`。  
验收标准：  
1. 同一 `request_id` 对应业务记录数为 `1`。  
2. 创建接口与查询接口 HTTP 2xx 比例为 `100%`（30 次调用）。  
3. `sql/ch12/accept.sql` 全部检查通过。  
4. 成功生成 `artifacts/ch12_delivery_pack.tgz`。

- 实验 B（进阶）
目标：在持续流量下完成灰度发布与回滚演练。  
前置条件：实验 A 通过；具备压测工具（`pgbench` 或 `hey`）；有发布脚本。  
步骤：  
1. 启动持续流量：`pgbench -c 64 -T 600 -f sql/ch12/pay_rw.sql`。  
2. 执行 `./release/canary.sh 10`，观察 10 分钟。  
3. 执行 `./release/canary.sh 50`，注入一次错误映射故障（模拟 SQLSTATE 冲突）。  
4. 执行 `./release/rollback.sh`，恢复后再升到 `100%`。  
5. 执行 `psql -f sql/ch12/accept.sql` 并归档报告。  
验收标准：  
1. 回滚动作完成时间 `<=5` 分钟。  
2. 灰度各阶段接口错误率 `<0.1%`。  
3. 回滚前后数据一致性检查均通过（空值/重复均为 `0`）。  
4. 全流程结束后 15 分钟内延迟恢复至基线区间（P95 不高于基线 +20%）。

## 6) 常见误区与纠偏（5 条）
1. 误区：接口先写，最后再对齐数据库字段。纠偏：先冻结 `数据契约 -> 服务契约`，再写代码。
2. 误区：幂等只放在应用缓存层。纠偏：数据库唯一约束与事务内检查必须同时存在。
3. 误区：所有数据库异常都返回 500。纠偏：按 `错误映射` 返回可判定错误码（如冲突、参数、不可重试）。
4. 误区：只做功能测试，不做灰度与回滚演练。纠偏：发布脚本和回滚脚本必须在压测流量下演练一次。
5. 误区：上线成功就算完成。纠偏：必须执行 `accept.sql` 和接口观测门禁后再收口。
