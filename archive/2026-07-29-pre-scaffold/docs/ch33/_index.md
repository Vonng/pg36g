## 1) 章节定位（一句话）
当 `PITR` 已无法在目标窗口内恢复业务时，本章聚焦“故障切换 + 故障主重建 + 服务验收”闭环，并产出可直接进入 `ch34` 的流量处置输入。

## 2) 学习完成标准（3-5 条，必须可验证）
1. 基于 `docs/ch32/ch33_input.yaml`，在 `10` 分钟内完成 `Go/No-Go` 切换决策记录。  
2. 完成 1 次主线故障切换，读写入口恢复时间（`T_failover`）`<= 8` 分钟。  
3. 切换后执行不少于 `8` 条验收 SQL，结果通过率 `100%`，并连续观察 `10` 分钟无新增写错误。  
4. 完成故障主重建并重新加入复制，复制延迟连续 `10` 分钟 `<= 10s`。  
5. 产出 `docs/ch33/ch34_input.yaml`，关键字段完整率 `100%`。  

## 3) 章节边界
本章要讲什么（5-7 条）
1. 如何承接 `ch32` 的升级条件，判断何时进入故障切换。  
2. 切换前如何做写入冻结与脑裂防护。  
3. 如何选择候选主并执行一次可控切换。  
4. 切换后如何做数据库与应用双验收。  
5. 如何重建故障主并恢复复制拓扑。  
6. `pg_rewind` 失败时如何走全量重拉兜底。  
7. 如何形成本章闭环交付并把输入传给 `ch34`。  

本章明确不讲什么（3-5 条）
1. 不讲 `PITR` 回放原理与误操作恢复细节（已在 `ch32`）。  
2. 不讲流量调度策略、灰度切流、服务降级编排（`ch34`）。  
3. 不讲司法取证、证据链和磁盘级数据抢救（`ch35`）。  
4. 不讲长期组织流程与平台治理制度设计。

## 5) 实战实验设计
实验 A（基础）  
目标：完成一次标准故障切换并恢复读写服务。  
前置条件：3 节点 HA 集群；`docs/ch32/ch33_input.yaml` 已存在；验收 SQL 已准备。  
步骤：  
1. 注入故障（主库不可达或停库）。  
2. 执行脑裂防护与候选主确认。  
3. 执行切换命令并确认新主角色。  
4. 验收读写入口与核心 SQL。  
5. 记录 `T_failover` 与错误率。  
验收标准：  
1. `T_failover <= 8` 分钟。  
2. 新主 `pg_is_in_recovery() = false`。  
3. 验收 SQL `>= 8` 条，`100%` 通过。  
4. 切换期间未出现双主（检测结果为 `0`）。  

实验 B（进阶）  
目标：完成“切换 + 故障主重建 + 交付 ch34 输入”闭环。  
前置条件：实验 A 通过；允许一次维护窗；可访问故障主数据目录。  
步骤：  
1. 先按主线完成切换与业务验收。  
2. 尝试 `pg_rewind` 重建故障主。  
3. 若失败（WAL 缺口），走支线 `pg_basebackup` 全量重拉。  
4. 观察复制稳定性 `30` 分钟。  
5. 输出 `docs/ch33/ch34_input.yaml`。  
验收标准：  
1. 重建耗时：`rewind <= 30` 分钟，或 `basebackup <= 60` 分钟。  
2. 复制延迟连续 `10` 分钟 `<= 10s`。  
3. 无新增复制错误日志。  
4. `docs/ch33/ch34_input.yaml` 字段完整率 `100%`。  

## 6) 常见误区与纠偏（5 条）
1. 误区：先切换后防脑裂。纠偏：先完成旧主隔离与不可写确认，再执行提升。  
2. 误区：只看“主从角色变更”就宣布成功。纠偏：必须做数据库 + 应用双验收。  
3. 误区：候选主延迟大也强行切换。纠偏：先校验延迟阈值，不达标先选其他候选或降级写入。  
4. 误区：`pg_rewind` 失败后反复重试。纠偏：满足失败条件即切到全量重拉，避免超时。  
5. 误区：重建完成但不输出交接输入。纠偏：必须量化残余风险并交付 `ch34` 输入文件。
